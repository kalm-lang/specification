# Changes planned for Kalm 1.2.0 (draft)

- **Baseline:** [1.1.0 final specification](../documents/v1.1.0.md).
- **Target:** [1.2.0 draft specification](../documents/v1.2.0-draft.md).
- **Status:** Draft, 2026-10-11.

This document describes the changes between those two specification editions. It compares against **final 1.1.0**,
not its earlier draft or the current compiler's behavior. The target specification is authoritative; this companion
explains compatibility and migration. These are planned requirements, not a claim that the compiler or libraries
already implement them. Despite the minor-version number, this draft includes breaking changes.

**Breaking** means previously valid source can fail, generated Java/JVM signatures change, or an existing API/behavior
contract changes. **Additive** means a new capability without removing an existing valid form. **Clarification** means
the old text was incomplete or contradictory; an implementation that chose a different interpretation may need changes.
New prelude names can also affect previously unresolved/import-dependent names; existing declarations in the current
Kalm scope still take precedence.

## Compatibility overview

| Change                                                          | Classification                                                | Required action or impact                                                                                                                 |
|-----------------------------------------------------------------|---------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------|
| Separate lowercase primitives from capitalized wrappers         | **Breaking: source, Java/JVM ABI, behavior**                  | Use lowercase types wherever primitive storage/signatures are intended; review overrides, fields, constants, annotations, and reflection. |
| Primitive literal inference and conversion results              | **Breaking: inferred types/API selection**                    | Review inferred locals, overload selection, and APIs exposing inferred results. Generic collections still box their elements.             |
| Non-null `Any`; nullable `Any?`                                 | **Breaking: source**                                          | Change null-capable `Any` bindings/results/parameters to `Any?`.                                                                          |
| `impl` → `implements`                                           | **Breaking: syntax**                                          | Rewrite implementation clauses; the old spelling is not a syntax alias.                                                                   |
| `choose`/`when` → `match`/`case`                                | **Breaking: syntax**                                          | Rewrite the matching construct and its arms.                                                                                              |

| Explicit modifiers for direct sealed children                   | **Breaking: source**                                          | Mark each direct child `fix`, `closed`, `extendable`, or `base`.                                                                          |

| Expanded standard library                                       | **Additive API contract**, plus primitive-signature migration | Preserve existing API capabilities; migrate primitive type spellings and implement the newly specified helpers.                           |
| Task result typing, cleanup, grammar, and conformance rules     | **Clarification/additive**                                    | Audit implementations against the explicit rules described below.                                                                         |

## Breaking changes and migration

### 1. Primitive and wrapper types become distinct

See draft [§3](../documents/v1.2.0-draft.md#3-types-values-and-java-mapping) and
[§7](../documents/v1.2.0-draft.md#7-packages-and-java-interoperability).

In 1.1.0 the capitalized built-in numeric/Boolean/character types represented primitives, with boxing in nullable or
generic contexts. In 1.2.0 the lowercase spelling is always primitive and the capitalized spelling is always the
corresponding non-null wrapper:

| Primitive spelling | Wrapper spelling | Java wrapper          |
|--------------------|------------------|-----------------------|
| `boolean`          | `Bool`           | `java.lang.Boolean`   |
| `byte`             | `Byte`           | `java.lang.Byte`      |
| `short`            | `Short`          | `java.lang.Short`     |
| `int`              | `Int`            | `java.lang.Integer`   |
| `long`             | `Long`           | `java.lang.Long`      |
| `float`            | `Float`          | `java.lang.Float`     |
| `double`           | `Double`         | `java.lang.Double`    |
| `char`             | `Char`           | `java.lang.Character` |

To retain a primitive API, change both parameter and result annotations:

```kalm
# 1.1.0: Java int square(int value)
pub fun square(value: Int) -> Int = value * value;

# 1.2.0 equivalent retaining primitive Java descriptors:
pub fun square(value: int) -> int = value * value;
```

Leaving `Int` unchanged now exposes `Integer square(Integer value)`. Kalm boxing may let calls continue to compile,
but the JVM descriptors differ. Already compiled Java/Kalm clients, reflection lookups, method references, and
primitive Java overrides can therefore break. Recompile dependents after an API descriptor change; merely recompiling
the provider is insufficient for old binary clients. Generated facade, accessor, external-wrapper, and record
constructor/component signatures need the same review. Public field descriptors change as well.

Additional consequences:

- `var count: Int;` is now a non-null reference field that needs initialization. Use `var count: int;` to retain the
  old primitive zero default, or initialize the wrapper explicitly.
- `constant LIMIT: Int = 100` must become `constant LIMIT: int = 100`. Boxed wrappers and nullable references cannot
  be Java compile-time constant types. Numeric/Boolean/character annotation elements likewise need primitive types.
- `Int?` remains a nullable `Integer`; it does not need a blanket rewrite. `Int` now explicitly excludes null.
  `int?` is invalid; use `Int?`. Apply the same rule to the other seven pairs.
- Keep `List<Int>` and `Array<Int>`: generic arguments/reference arrays use wrappers. `List<int>` and `Array<int>`
  are invalid. `IntArray` and the other primitive-array types retain primitive storage.
- Numeric and Boolean literals infer lowercase primitives; character literals infer `char`. `L` and `f`/`F`
  suffixes produce `long` and `float`; other floating literals produce `double`. Numeric conversions such as
  `toInt()` return the primitive, which may then box for a wrapper target.
- An existing alias such as `alias UserId = Long` now denotes a wrapper. Use `long` to preserve primitive storage.
  New built-in lowercase spellings cannot be redeclared as types/aliases; rename conflicting custom aliases/types.
- Boxing, unboxing, widening, and overload selection follow Java, subject to nullability. Widening an `int` and then
  boxing directly to `Long` is not implicit; supply a `long` expression. Representable constant narrowing in Java
  assignment contexts is allowed; arbitrary runtime narrowing still uses checked conversions.
- Arithmetic unboxes non-null wrappers and uses Java promotion, including mixed numeric widths. Its result is a
  primitive. `byte`, `short`, and `char` promote to `int`; wider operands select `long`, `float`, or `double`.
- Wrapper equality is Java value equality, not identity. `Int` and `Long` wrappers do not compare equal solely
  because their numbers match; convert/unbox when numeric promotion is intended. Nullable wrappers must be
  refined/coalesced before operations that require unboxing.

Checked narrowing, integer wrapping overflow, truncating integer division, and primitive-array capabilities are
preserved. The draft also explicitly states division-by-zero, floating-point, Unicode-character, and minimum-signed-
literal rules that were incomplete in the old text.

### 2. `Any` no longer accepts null

1.1.0 explicitly allowed null to target `Any`; 1.2.0 consistently treats it as non-null `java.lang.Object`.

```kalm
# 1.1.0:
var value: Any = null;

# 1.2.0:
var value: Any? = null;
```

Review parameters, results, fields, and generic arguments as well as locals. A value declared `Any` must be present;
primitives assigned to it box normally. Null-aware printing still works because `text`, `say`, and `sayLine` accept
`Any?`. This is primarily a source/nullability-contract change, not a change from `Object` to a different JVM class.

### 3. Renamed syntax has no legacy aliases

```kalm
# 1.1.0:
class Service impl Runnable { ... }
fix message = choose status {
    when Status.Ready => "ready";
    when Status.Failed => "failed";
};

# 1.2.0:
class Service implements Runnable { ... }
fix message = match status {
    case Status.Ready => "ready";
    case Status.Failed => "failed";
};
```

The class-body ellipses above indicate unchanged code, not literal Kalm syntax. Rewrite implementation clauses,
matching expressions/statements, grammar consumers, formatter/highlighter rules, and generated examples. `impl`,
`choose`, and `when` are ordinary identifier spellings in 1.2.0, not deprecated spellings of the removed constructs.

### 4. Classes and methods are open by default

See draft [§6](../documents/v1.2.0-draft.md#6-classes-contracts-and-visibility).

Ordinary 1.1.0 classes/methods were final unless made extendable. Ordinary 1.2.0 classes and eligible instance
methods can be inherited/overridden. Contract implementations and concrete implementations of abstract requirements
also remain overridable unless marked `fix`; generated forwarding methods follow that rule.

```kalm
# 1.1.0's default finality, preserved explicitly in 1.2.0:
fix class Service {
    fun run() { sayLine("running"); }
}

# An open class with one explicitly final method:
class BaseService {
    fix fun stable() -> Text = "stable";
}
```

This does not generally make an existing ordinary declaration fail compilation. It changes its API guarantees and
Java final modifiers, and newly legal overrides can change dispatch behavior. Add `fix` wherever callers/providers
rely on the old final contract. `fix` bindings still mean immutable bindings; that meaning is unchanged.

`base` remains abstract, `closed` remains sealed, and `extendable` remains an explicit open/non-sealed marker.
Private methods, constructors, and top-level functions do not become overridable. Records and singletons remain
final, and choices retain Java enum restrictions. Invalid modifier combinations remain errors.

Every direct child of a `closed` hierarchy now needs an explicit `fix`, `closed`, `extendable`, or `base` modifier.
An unmarked child that used to become final must be marked `fix`; leaving it unmarked is a source error.

### 5. Prefix words followed by parentheses are calls

Contextual keyword names are permitted in declaration-name, binding/parameter-name, member-name, and unambiguous
call positions. This enables `and()`, `test()`, and similarly named members. Literal words remain reserved.

The ambiguity policy intentionally changes grouped word-operator syntax, regardless of whitespace:

```kalm
# 1.1.0 operator forms:
# not (paused)
# await (pending)

# 1.2.0 operator forms:
# !(paused)
# not paused
# await pending
# await client.fetch()
```

In 1.2.0 `not(paused)` and `await(pending)` resolve named callables; they fail if no such callable exists. Infix
`and`/`or` still act as operators between operands. Complete control constructs retain their grammar; `test()` is a
call, whereas `test "description" { ... }` is a test declaration. Contextual recognition does not excuse malformed
constructs or missing bodies.

## Clarifications that may require migration

These do not all represent removal of an unambiguously valid 1.1.0 program. They settle gaps or conflicts where
different implementations could previously behave differently.

| Area                      | Exact 1.2.0 rule                                                                                                                                                                                                          | Compatibility consequence                                                                                                                                                               |
|---------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Logical precedence        | `and`/`&&` bind more tightly than `or`/`\|\|`; each pair has identical short-circuit behavior.                                                                                                                            | The 1.1.0 grammar already said this, but its table grouped both levels together. Explicitly parenthesize if old table grouping was intended. Symbolic aliases already existed in 1.1.0. |
| Java platform nulls       | Assignment from an unannotated Java reference still warns; null entering a non-null Kalm reference slot raises `NullPointerException`.                                                                                    | Existing code relying on a warning alone and retaining a null in a non-null slot can now fail earlier. Use nullable types when Java can return null.                                    |
| Ordinary map indexing     | A missing key yields a nullable result even when the map value argument is non-null. Safe indexing additionally accounts for a null receiver.                                                                             | Non-null assignment may need `map[key] ?? fallback` or another absence check. The old text explicitly covered missing keys only in safe indexing.                                       |
| Value matching            | Every value-producing match is exhaustive; nullable subjects need null coverage, Boolean subjects need both values, and open/infinite domains normally need `_`.                                                          | Partial value matches need coverage. Statement matches may now be partial and do nothing when unmatched. 1.1.0 explicitly required exhaustiveness only for choices/sealed hierarchies.  |
| Match block results       | Completing value-arm paths use `yield expression`; `return` exits the enclosing function/lambda/task. A value match cannot yield `Unit`.                                                                                  | Review old block arms because their result mechanism was underspecified. Do not mechanically replace every arm-local return with yield if it was intended to exit the function.         |
| Match arm order           | Subject evaluated once, first matching arm selected, no fallthrough; `_` last; duplicate/provably unreachable arms rejected.                                                                                              | Remove unreachable arms or reorder overlapping type patterns. Null subjects match only `null`/`_`.                                                                                      |
| Public result annotations | Public value-producing functions still require explicit result types; an omitted arrow on a block body expresses `Unit`, including for public functions. Non-public expression bodies may infer results.                  | Resolves the conflict between the old explicit-public-result requirement and omitted-block-arrow rule. It does not infer a value result for unannotated block functions.                |
| User/library overloads    | One source function name per scope; Java/prelude overloads and generated default-argument overloads are allowed separately.                                                                                               | Existing manual Kalm overloading remains unsupported. Generated default helpers do not create a general overload feature.                                                               |
| Tasks and `Unit`          | Primitive async results box in `Task<T>`; `Task<Unit>` and `CompletionStage<Unit>` use Java `Void`. Awaiting those forms produces no stored Kalm value.                                                                   | Resolves the old result-only `Unit` rule conflicting with generic task results. Ordinary `Unit` collections/parameters remain invalid.                                                  |
| Task-block inference      | An expected task type controls completion. Without one, compatible value returns infer a result; bare return/fallthrough adds nullability; only no-result completion infers `Task<Unit>`.                                 | Audit implementations that always required an explicit returned value. Non-null targets still require values on every normal completion path.                                           |
| Checked exceptions        | Ordinary functions still cannot leak checked exceptions; a corresponding Java override/SAM body may propagate exceptions its Java signature permits.                                                                      | Relaxes the old blanket handling wording while preserving Java-compatible throws information and ordinary-function restrictions.                                                        |
| Resources and defer       | Resource closing uses Java suppression. Defers belong to the innermost lexical block; all run in reverse registration order even if one fails, with primary/suppressed failure rules. Cleanup precedes delivered results. | Review implementations that stopped cleanup at the first failure or selected a different primary exception. `yield` joins the prohibited control transfers inside defer.                |
| Constants and annotations | Constants require Java-compatible primitive/Text compile-time expressions; wrappers/nullable types are not constant types. Java annotation elements use Java-supported element types.                                     | Primitive-spelling migration is breaking as described above; expression eligibility is now stated precisely.                                                                            |
| Grammar and tokens        | Explicit script, binding/default, primitive, match/yield, branch-alias, and empty-separator productions; block-end termination is lookahead, not delimiter consumption.                                                   | Parser/tooling conformance changes; the old contextual shorthand and incomplete productions are no longer sufficient.                                                                   |
| Record properties         | A record component is a read-only Kalm property and keeps its component-named Java accessor.                                                                                                                              | Clarifies how record-backed helper results such as `Timed.elapsed` are accessed; it does not add mutable record components.                                                             |
| Literals and escapes      | Literal types are explicit; newline/tab/Unicode escape spellings are corrected; character escapes/code-unit limits and minimum signed literals are stated.                                                                | Corrects presentation gaps without adding hex/octal/separator literal syntax.                                                                                                           |

## Compatible language additions

### Multiple declarations and flat bracket bindings

Both mutable and immutable declarations support multiple names:

```kalm
var a = 5, b: int = 7, c: Int = 8;
fix [left: Int, right: Int] = [5, 7];
var [count, label] = [5, "five"];
```

Independent initializers evaluate left to right and may use earlier names. Each field in a comma declaration must
have its own explicit type. Bracket bindings are local/script declarations only, over contextual literals, lists,
reference arrays, or primitive arrays. They evaluate the source once, require exact length, and complete extraction/
conversions before initializing any destination. Literal length/type mismatches are compile errors; dynamic length
mismatches raise `IllegalArgumentException`. Nested/rest/skipped bindings and destructuring reassignment are excluded.

### More completion forms, with strict signatures

- Omitted block-function result arrows still mean `Unit`. No return, bare return, and literal `return null` are allowed.
  Other value returns remain errors; the literal-null form emits Java no-result completion.
- Explicit nullable results allow bare return or normal fallthrough as null, in addition to a compatible value/null.
- Explicit non-null results still require compatible returned values on every reachable normally completing path.
- Apply the result contract to methods, getters, target-typed lambdas, and async bodies; constructors/setters/hooks use
  no-result rules. A block's final ordinary expression is not implicitly returned.

### Defaults on concrete named functions, methods, and constructors

Trailing defaults use `parameter: Type = expression`. Calls remain positional and may omit only a suffix. Explicit
null never triggers a default. Supplied arguments run once left to right, then omitted defaults once in parameter
order for each invocation. Earlier parameters may be referenced; references to the parameter being defaulted or a
later parameter, and required-after-default parameters, are invalid. Instance-method defaults may use `self`, but
constructor defaults cannot access an unconstructed instance; defaults cannot use await.

Overrides inherit defaults and cannot redefine them. Abstract/contract/external declarations, data components,
accessors, and lambda parameters cannot introduce defaults. Java receives the full signature plus suffix-omission
overloads; instance forwarding overloads are final and dispatch to the full virtual method. Erased-signature
collisions are errors. Adopting defaults therefore expands a Java API and can affect Java overload selection,
even though functions that do not adopt defaults retain their call forms.

### Separators and branches

Repeated/standalone `;` separators are accepted across declaration and statement bodies. They do not repair a missing
initializer/expression/body or make a separator-only colon suite nonempty. `else if` becomes an alias for `elif`,
including both brace and colon blocks. Neither addition changes valid existing simple statements or `elif` chains.

## Newly specified script and documentation contracts

### Kalm Script (`.kalms`)

The draft explains when to use compiled application/library source versus scripts and adds a formal script grammar.
Scripts share Kalm typing and syntax, permit sequential top-level statements/declarations/imports, and require neither
`space` nor `main`. Declaring `main` does not invoke it. Package/test/hook declarations and top-level return/yield/await
are rejected; referenced names must exist before use, with self-recursion allowed.

The baseline host contract covers `kalm shell`, `-e`/`--eval`, `-f`/`--file`, mutually exclusive inputs, full JDK 25+,
and JDK/bundled Kalm dependencies only. It does not supply project discovery, arbitrary classpaths, or dependency
downloads. Portable scripts use `.kalms`; compatibility acceptance of `.kalm` requires a warning.

Session rules cover persistent definitions/objects, no replay, result display/names, preflight-checked replacement,
type-layout restrictions, continuation input, commands, EOF for evaluated code, piped input, diagnostic formats, and
exit statuses. File/inline/piped execution stops at its first failure; prior side effects remain. Interactive errors
leave the session available. These rules document and constrain an existing repository feature; they do not mean
that scripting is being introduced for the first time by this document.

### KalmDoc

Consecutive `###` lines now have a defined attachment and documentation language rather than preservation merely
“where practical.” Blank lines/unrelated syntax end attachment; annotation/modifier lines do not detach a comment
from its declaration. Descriptions use Javadoc-compatible text/HTML rather than a separate Markdown dialect.

Required block tags are `@param`, `@return`, `@throws`, `@see`, `@since`, and `@deprecated`; required inline tags are
`{@link}`, `{@code}`, `{@literal}`, and `{@inheritDoc}`. Documentation-capable generators must produce valid Java
doc comments/stubs, resolve Kalm types and symbols to their generated Java forms, escape comment terminators, attach
facade/accessor/record documentation correctly, and preserve nullability/default/async-result information.
Default-argument overload documentation excludes omitted parameter tags but retains omission notes. Generated
`@apiNote` requires custom-tag registration or equivalent rendered description content; the draft includes a working
JDK 25 invocation. Doc deprecation text alone does not replace the `legacy` modifier's runtime/compiler metadata.

New warning codes `KALM-4001` through `KALM-4005` cover orphan groups, invalid targets/parameters/inheritance,
unresolved references, malformed/duplicate tags, and unknown tags. Warnings do not fail program compilation; an
optional strict documentation mode may fail documentation generation. Existing source comments remain comments,
but an implementation conforming to the new documentation contract must handle them as specified.

## Standard-library changes

See draft [§8](../documents/v1.2.0-draft.md#8-standard-library) for complete signatures, defaults, exceptions,
and edge cases. The following list identifies every added/newly formalized API family:

| Family                  | Added/newly formalized APIs                                                                                                                                                          |
|-------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Console                 | `text`, no-argument `sayLine`, `readLine()`, and `readLine(prompt)`; line input yields null at EOF.                                                                                  |
| Text                    | `upper`/`lower` retained and specified; new `trimmed`, `isBlank`, literal `splitOn`, and literal `replaceText`, also exposed through `Texts`.                                        |
| Parsing                 | Nullable `parseByte`, `parseShort`, `parseInt`, `parseLong`, `parseFloat`, `parseDouble`, and `parseBool`; invalid/out-of-range input yields null under the specified parsing rules. |
| Collection factories    | `listOf`, insertion-ordered `setOf`, and `mapOf(keys, values)`; reference/primitive array factories retained with explicit fresh-storage behavior.                                   |
| Traversal               | `map`, `filter`, `fold`, both `firstOrNull` forms, `any`, `all`, and `join`; encounter order, empty-input results, and callback/short-circuit counts are specified.                  |
| Ranges/math             | Existing ranges retained; add signed nonzero `step` with overflow-safe lazy progression. Add primitive `clamp` overloads and explicit floating-bound rules.                          |
| Array adaptation        | `Collections.asList` for reference/all primitive arrays, producing fresh boxed snapshots for Iterable-based helpers.                                                                 |
| File/path facade        | `FileOps.path`, `resolve`, `exists`, `readText`, `readLines`, `writeText`, and `appendText`; UTF-8 defaults, resource closure, checked-I/O wrapping, and non-atomic-write behavior.  |
| Time facade             | `Time.now`, `todayUtc`, `millis`, `seconds`, and `timed`; UTC calendar/timeline helpers and monotonic duration measurement.                                                          |
| Task facade             | `Tasks.all`, `withTimeout`, and `mapConcurrent`; ordered results, bounded virtual-thread callbacks, deadlines, cancellation, and failure races.                                      |
| Collection conveniences | `Collections.windowed` with size/step/partial controls and single-pass `partition`.                                                                                                  |
| Callback contracts      | `Mapper<T,R>`, `Predicate<T>`, `Folder<A,T>`, and `Supplier<T>`.                                                                                                                     |
| Result records          | `Partition<T>(matching, remaining)` and `Timed<T>(value, elapsed)`.                                                                                                                  |

Every original prelude capability remains: printing, `len`, arrays, the original range overloads, `exit`, numeric
`abs`/`min`/`max`, `sqrt`/`pow`/`round`, and locale-independent case conversion. Primitive-signature annotations are
updated to lowercase spellings, while collections/task values use wrappers. Do not infer that every newly documented
helper is absent from current code; this comparison is against the final 1.1.0 specification's API contract.

Everyday helpers are in the default prelude. File/time/task/advanced-collection facade APIs require explicit imports.
Existing Kalm scope declarations continue to take precedence over prelude names; real Java instance methods take
precedence over extensions. Lists/maps remain mutable Java collections. Returned helper collections are fresh
snapshots unless a signature says otherwise; window lists do not structurally share backing storage. Partition/Timed
records have immutable component bindings, while contained objects/lists retain their own mutability.

## Specification and repository changes

- The new document is copied and extended from final 1.1.0; all original sections and historical editions remain.
  Requested replacements are reflected consistently in prose, mappings, examples, keyword rules, and grammar.
- Metadata is `1.2.0`, `draft`, date/last-modified `2026-10-11`, with Java baseline still `25`.
- New dedicated sections cover Kalm Script, migration from final 1.1.0, and future conformance scenarios; KalmDoc and
  the expanded library are integrated into the existing interoperability/library sections.
- The README and generated package index expose the new draft; `latestVersion` remains the latest final, `1.1.0`.
- This `changes/` companion is explanatory repository documentation; it is not an additional language edition in
  `documents/` and does not change version selection.

The compiler, CLI implementation, runtime implementation, editor extensions, and publishing have not been changed
as part of writing these specification documents. Syntax acceptance, Java descriptors, library behavior, doc
conversion, and the listed error cases are acceptance requirements for a future conforming 1.2.0 implementation.
